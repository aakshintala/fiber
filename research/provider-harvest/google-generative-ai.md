# google-generative-ai wire protocol: pi and rig side by side

Two reference implementations of Gemini's `generateContent` /
`streamGenerateContent` wire, read line by line. pi is
`@earendil-works/pi-ai` 0.87.1 (`pi-ai/package.json`, installed at
`/opt/homebrew/lib/node_modules/@earendil-works/pi-coding-agent/node_modules/@earendil-works/pi-ai/`),
which does not speak raw HTTP to Gemini: it calls the official
`@google/genai` SDK, version 2.21.0, vendored alongside it
(`node_modules/@google/genai/dist/node/index.mjs`, 26,337 lines,
unminified). Facts that live in the SDK rather than in pi's own adapter are
cited against that file and called out as such. rig is the checkout at
`~/work/rig`, commit `42f4e06` (`crates/rig-core/src/providers/gemini/`),
which speaks the wire directly with no vendor SDK. File paths below are
relative to each of those two roots unless given in full. This table
restates facts from `research/rig/README.md` and
`research/provider-errors/README.md` only where it adds the pi side; see
those files for rig-only detail already captured there.

## 2. Stream event types and the terminal event

| Fact | pi | rig | Mark |
|---|---|---|---|
| Chunk shape | Each SSE `data:` line is one `GenerateContentResponse` with `candidates[0].content.parts`, `candidates[0].finishReason`, `usageMetadata`, `responseId` (`google-generative-ai.js:57-186`) | Same JSON shape decoded into `GenerateContentResponse`/`ContentCandidate`/`Part` (`streaming.rs:146-262`, types at `completion.rs:547-613`) | agree |
| Recognizing a genuine chunk vs. noise | not applicable — the SDK hands pi only already-parsed `GenerateContentResponse` objects; pi does no frame classification of its own | `RECOGNIZABLE_CHUNK_KEYS = ["candidates","usageMetadata","promptFeedback","error"]`; a frame with none of them, but with a bare `responseId`, is treated as identity-only metadata rather than an unknown/truncating frame (`streaming.rs:94-168`) | rig only |
| `responseId` | Documented as SDK output-only; pi keeps the **first** non-empty one seen across the stream (`output.responseId ||= chunk.responseId`, `google-generative-ai.js:55-57`) | Keeps the **last** non-empty one, overwriting on every chunk that carries it, then reports it on the terminal record (`streaming.rs:178-181,296,309`) | disagree |
| `finishReason` values pi/rig map | pi: only `STOP`→`stop` and `MAX_TOKENS`→`length` are distinguished; every other value (`SAFETY, BLOCKLIST, PROHIBITED_CONTENT, SPII, RECITATION, LANGUAGE, MALFORMED_FUNCTION_CALL, UNEXPECTED_TOOL_CALL, TOO_MANY_TOOL_CALLS, IMAGE_*, OTHER, FINISH_REASON_UNSPECIFIED, NO_IMAGE`) maps to the single stop reason `"error"` (`google-shared.js:383-411`, exhaustive switch against the SDK's `FinishReason` enum, `@google/genai/dist/node/index.mjs:1046-1120`) | rig distinguishes a third bucket: `STOP`→`Stop`, `MAX_TOKENS`→`Length`, `{SAFETY,BLOCKLIST,PROHIBITED_CONTENT,SPII}`→`ContentFilter`, and everything else (including `RECITATION`, `LANGUAGE`, `MALFORMED_FUNCTION_CALL`, `UNEXPECTED_TOOL_CALL`, `TOO_MANY_TOOL_CALLS`, `MISSING_THOUGHT_SIGNATURE`, `MALFORMED_RESPONSE`) → `Other(raw_string)` (`completion.rs:1400-1410`) | disagree |
| Finish reasons rig knows that pi's pinned SDK does not | — | rig's own `FinishReason` enum additionally declares `MissingThoughtSignature` and `MalformedResponse`, Gemini 3-era values absent from `@google/genai` 2.21.0's `FinishReason` enum entirely (compare `completion.rs:1333-1367` to `index.mjs:1046-1120`) | rig only |
| Tool-call finish reason as a hard failure | pi has no separate handling; `MALFORMED_FUNCTION_CALL`/`UNEXPECTED_TOOL_CALL`/`TOO_MANY_TOOL_CALLS` fall into the generic `"error"` stop reason bucket above | `tool_protocol_finish_reason_error` turns these into a distinct `ProviderError` before any content is emitted, via `function_call_finish_reason_error` (`streaming.rs:83-86,234-238`) | disagree (rig gives these a dedicated error path; pi folds them into its one generic error stop reason) |
| stopReason override for tool calls | If the mapped stop reason is `"stop"` but the message contains a `toolCall` block, pi overrides it to `"toolUse"` (`google-generative-ai.js:164-166`) | not applicable — rig's normalized `FinishReason` has no such override; tool-call presence is represented structurally by stream blocks, not by reinterpreting the finish reason | pi only |
| `usageMetadata` fields read | `promptTokenCount, cachedContentTokenCount, candidatesTokenCount, thoughtsTokenCount, totalTokenCount`; `input` is computed as `promptTokenCount - cachedContentTokenCount` (`google-generative-ai.js:168-183`) | `UsageMetadata` also models `promptTokensDetails, cacheTokensDetails, candidatesTokensDetails, toolUsePromptTokenCount` in addition to the same core fields (`completion.rs:1216-1243`); the observation/telemetry projection separately reads `tool_use_prompt_token_count` (`streaming.rs:330-337`) | disagree (rig's usage struct is a superset; pi never reads `toolUsePromptTokenCount`) |
| `cacheWrite` | Always hardcoded to `0` — pi has no implicit-cache-write accounting (`google-generative-ai.js:173`) | rig's `Usage` conversion from `UsageMetadata` likewise has no cache-write field (Gemini's API does not report one) | agree |
| Terminal signal, unary mode | not applicable (pi's adapter only speaks the streaming SDK method) | `whole: mode == Mode::Unary`; on unary EOF, an empty response with no truncating finish reason is a hard error (`EMPTY_RESPONSE_ERROR`), rather than being read as a valid empty completion (`streaming.rs:118-119,264-277`) | rig only |
| Terminal signal, streaming mode | The `for await` loop ends when the SDK's async generator completes; pi then requires `output.stopReason` to not still be `"pending"`, else throws `"Google stream ended without a finish reason"` (`google-generative-ai.js:186-210`) | `is_finished()` only reports done via `self.failed`; a stream whose reader closes without ever setting a finish reason (`saw_finish_reason` false) simply produces no terminal record rather than a synthesized error (`streaming.rs:264,280-282,314-317`) | disagree |
| No `[DONE]` sentinel | Gemini's SSE has no OpenAI-style `[DONE]` marker; pi relies entirely on the SDK's stream ending (see above) | Same; rig's decoder has no `[DONE]` handling anywhere in `streaming.rs` | agree |

## 3. Tool-call assembly

| Fact | pi | rig | Mark |
|---|---|---|---|
| `functionCall` parts stream as one whole object, never incrementally | Each `part.functionCall` is a complete `{name, args, id?}`; pi immediately emits `toolcall_start`, one `toolcall_delta` with the full stringified arguments, then `toolcall_end` for that single chunk — arguments never arrive as partial JSON fragments across multiple chunks (`google-generative-ai.js:116-158`) | Same assumption: `shared_parts::function_call` emits a paired `BlockStart`/`BlockEnd` from one whole `FunctionCall{name, args, id}` with no intermediate delta state (`streaming.rs:28-55,471-494`) | agree |
| Parallel tool calls | Multiple `functionCall` parts in one `candidate.content.parts` array each get their own start/delta/end triple in order (`google-generative-ai.js:59-159` loop) | Multiple `Part`s in one `content.parts` are each dispatched to `interpret_part` in order (`streaming.rs:240-255`) | agree |
| Missing call id (Gemini omits it) | pi generates a synthetic id `${name}_${Date.now()}_${++toolCallCounter}` whenever `part.functionCall.id` is absent **or** would collide with an id already used in this message (`google-generative-ai.js:136-141`) | rig mints a synthetic local `BlockId` via `SyntheticIds` when the wire supplies no non-empty id, but deliberately leaves `ToolCallEnd.tool_id` unset in that case rather than inventing a provider identity — "setting call_id as well would invent a second provider identity" (`streaming.rs:36-43`) | disagree (pi's synthetic id is sent back to the model as if it were a real provider id on replay; rig's synthetic id is a local bookkeeping key only, never presented as the provider's own id) |
| Gemini major-version gate on whether an explicit id is required at all | `requiresToolCallId(modelId)`: true for `claude-*`, `gpt-oss-*` (Cloud Code Assist passthrough models), and Gemini major version ≥ 3; false (id omitted from the wire) for Gemini 1/2.x (`google-shared.js:120-134,227-238,268-276`) | No such gate: `FunctionCall.id`/`FunctionResponse.id` are serialized whenever the internal `ToolCall`/message carries a provider id, regardless of Gemini model version (`completion.rs:1114-1122,1126-1132`, encode call sites at `completion.rs:883,1082,1119`) | disagree |
| Tool call id normalization | For models that require ids, pi rewrites them to `^[a-zA-Z0-9_-]{1,64}$` — non-matching characters become `_`, length capped at 64 (`google-shared.js:149-153`); a separate cross-provider pass in `transform-messages.js` maps original→normalized ids so tool results still match (`transform-messages.js:39-46,100-113`) | No id-shape normalization found in the Gemini wire code | pi only |
| `functionResponse` shape | `{functionResponse: {name, response: {output|error}, parts?, id?}}`; the response value is always `{output: text}` on success or `{error: text}` on failure, never a raw arbitrary object (`google-shared.js:260-276`) | `FunctionResponse{name, id, response: Option<Value>, parts}` — `response` is the arbitrary JSON value from `crate::message` with no output/error wrapper key imposed (`completion.rs:1124-1139`, encode site `completion.rs:826-889` region) | disagree |
| Merging function responses into one turn | "Cloud Code Assist API requires all function responses to be in a single user turn" — pi appends a new `functionResponse` part onto the previous `user` content if that content already holds one, rather than opening a new turn (`google-shared.js:277-288`) | not found — no equivalent merge-into-one-turn logic in `completion.rs`'s history conversion | pi only |
| Multimodal function response (image results) | Gated by Gemini major version: `supportsMultimodalFunctionResponse` nests images inside `functionResponse.parts` only for Gemini ≥ 3; for Gemini < 3 (and Claude-via-Cloud-Code-Assist) the image goes in a separate following `user` turn with the images as plain `inlineData` parts (`google-shared.js:135-141,256-296`) | `FunctionResponsePart{inline_data, file_data}` always available on `FunctionResponse.parts` with no model-version gate (`completion.rs:1141-1164`) | disagree |
| Orphaned tool calls (no result ever arrives) | `transform-messages.js` synthesizes an error tool result, `"No result provided"`, for any tool call left unanswered when a new user turn or the end of history is reached, preserving thought signatures on the calls (`transform-messages.js:125-153,188-198`) | not found as a distinct pre-encode pass in the Gemini wire; rig's `resolve_empty_tool_result_names` (`completion.rs:165`) fixes up empty `functionResponse.name` values but does not synthesize a missing result | pi only |
| Thinking-signature-bearing empty part is still emitted as a tool call boundary | thought signature can also land on a `functionCall` part itself (not just text); pi keeps it as `toolCall.thoughtSignature` when present (`google-generative-ai.js:147`) | rig carries the same signature through `shared_parts::function_call`'s `signature` parameter onto `ToolCallEnd::with_signature` (`streaming.rs:31-43,483-489`) | agree |

## 4. Thinking: thought parts, thoughtSignature, cross-model handling

| Fact | pi | rig | Mark |
|---|---|---|---|
| What marks a part as thinking | `part.thought === true` is the only marker checked; `thoughtSignature` can appear on any part type and does not itself mean "thinking" (`google-shared.js:73-90`, doc comment citing `ai.google.dev/gemini-api/docs/thought-signatures`) | Same: a `Part` is thinking only when `thought == Some(true)`; a signature on plain text is handled as a property of that text part, not as thinking content (`streaming.rs:423-470`) | agree |
| Signature arrives once or streamed | pi's `retainThoughtSignature` keeps the last non-empty signature seen across multiple deltas for the same open block, because "some backends only send `thoughtSignature` on the first delta ... later deltas may omit it" (`google-shared.js:91-104`) | Every observed Gemini `FunctionCall`/text/thinking part in rig's decoder carries at most one signature per whole `Part` (Gemini's REST/SSE wire, unlike the streamed proto delta case pi's comment describes, sends one complete part per `functionCall`) — no multi-delta accumulation logic exists because rig never sees a functionCall arrive incrementally in the first place (see §3) | pi only (the accumulation logic exists because pi's comment anticipates deltas that, per rig's implementation of the same wire, do not occur for `functionCall`; may be a defensive no-op for a case that never fires on this protocol, or evidence of a partial-delta behavior rig has not observed) |
| Signature riding on empty text | An empty text block is dropped **unless** it carries a signature; a signature can be on an otherwise-empty text part and must be echoed back or "the model intermittently ends mid-task turns with a thought-only STOP" (`google-shared.js:190-201`, comment) | A signed empty text part still ends the active text block explicitly (`out.end_active_text()`) rather than being silently dropped (`streaming.rs:451-470`) — same underlying wire behavior, opposite direction (decode vs. encode) | agree (same fact, observed on encode by pi and on decode by rig) |
| Signature validity check before replay | pi validates the signature is base64 (`^[A-Za-z0-9+/]+={0,2}$`, length a multiple of 4) before resending it, and only when `isSameProviderAndModel` (`google-shared.js:105-119`) | No equivalent base64/shape validation found on the encode side in `completion.rs`; rig passes whatever signature string it decoded straight back through `text_signature_extras`/`FunctionCall.thought_signature` when replaying (`gemini/mod.rs:66-84`) | pi only |
| What crosses a model switch | Thinking blocks and text-block signatures are kept **only** when `msg.provider === model.provider && msg.model === model.id` (same provider and exact model); otherwise thinking text becomes plain text with no signature, and a `toolCall.thoughtSignature` is deleted (`google-shared.js:188-238`; `transform-messages.js:66-115` applies the identical rule generically across protocols, also checking `api`) | rig's model does not do same-model gating in the Gemini wire itself — the thought signature is stored in a text block's `additional_params` (`GEMINI_TEXT_EXTRAS_KEY`) or the tool-call's signature field and is echoed back whenever it is present on replay, with no visible cross-model/cross-provider check in `completion.rs`/`gemini/mod.rs` | disagree |
| Redacted/opaque thinking dropped across model switch | pi drops a `redacted` thinking block entirely on any model switch, keeping it only for the exact same model (`transform-messages.js:74-77`) | Gemini's wire has no separate "redacted thinking" variant (that is an Anthropic/OpenAI concept per `research/rig/README.md` §3); not applicable to this protocol on either side | — |
| Where the signature lives on the wire | On the `Part` itself, `thoughtSignature`, sibling to `thought` and `text`/`functionCall` (`google-shared.js:198-237`) | Same field name and position, `Part.thought_signature` (`completion.rs:651-662`); rig additionally re-exposes it off-band on decoded text blocks via `GEMINI_TEXT_EXTRAS_KEY`/`text_thought_signature` so a consumer can read "the signature Gemini put on this answer text part" without re-parsing the wire part (`gemini/mod.rs:57-84`) | agree |

## 6. Error bodies, retry signals, context-overflow shapes

| Fact | pi | rig | Mark |
|---|---|---|---|
| In-band `error` object inside an otherwise-200 SSE stream | The SDK's `processStreamResponse` has a pre-check that tries `JSON.parse(chunkString)` on the **raw, undelimited** bytes just read from the network and looks for an `"error"` key (`@google/genai/dist/node/index.mjs:13798-13816`) — but a genuine `alt=sse` frame is `data: {...}\n\n`, which is not valid JSON on its own, so this `JSON.parse` throws and is silently swallowed (only rethrown if the caught error's `name` is already `"ApiError"`, which it never is at that point). The later, correct per-event parse (`index.mjs:13843-13858`) discards the event into a `GenerateContentResponse` via `generateContentResponseFromMldev`, which never reads an `error` key at all (`index.mjs:10894-10933`). Net effect: a genuine mid-stream Gemini error frame is silently dropped as an empty chunk, and pi's own code eventually throws the generic `"Google stream ended without a finish reason"` once the stream closes (`google-generative-ai.js:208-210`) | The decoder explicitly lists `"error"` as one of `RECOGNIZABLE_CHUNK_KEYS` (`streaming.rs:94-95`) and, on seeing it, reads `error.code` as an HTTP status if it parses as one in the client/server error range, producing `ProviderError::from_http_response(status, body)` (participating in the shared retry table), or `ProviderError::from_provider_body(body)` otherwise (`streaming.rs:192-210`) | disagree |
| `promptFeedback` block (prompt itself refused) | Not read anywhere in `google-generative-ai.js`/`google-shared.js` — a blocked prompt is not specially detected; it would fall through to the same "stream ended without a finish reason" generic error as above, if `candidates` is ever empty | Explicitly handled: `blocked_prompt_error` converts `promptFeedback.blockReason` into a distinct `ProviderError` rather than an unexplained truncation (`streaming.rs:212-217`) | rig only |
| HTTP-level (non-2xx) error shape read from the body | `throwErrorIfNotOK` (SDK): JSON body parsed as-is when `content-type` is `application/json`; otherwise wrapped as `{error:{message: <raw text>, code: <http status>, status: <status text>}}`. | Does the SDK's `ApiError` carry response headers (for `Retry-After`)? | No. `ApiError` has only `message` and `status`; `headers` is never set (`index.mjs:7791-7798`). pi's own `retryGoogleRequest` has to work around this: `if (error instanceof Error && "status" in error && !("headers" in error)) { error.headers = undefined; }` before rethrowing (`google-shared.js:434-450`), explicitly because "The SDK's ApiError has a `status` property but no `headers` property" (comment, `google-shared.js:425-433`) | Not applicable in the same way — rig's HTTP client preserves headers on a non-2xx response as part of `ProviderResponse` generically (`research/rig/README.md` §5, `error.rs:44-48`) | pi only |
| Consequence: does pi ever honor a Gemini `Retry-After` header? | No. Because the SDK's `ApiError` never carries headers, `getRetryDelayMs`'s header lookups (`error.headers?.get("retry-after-ms")`, `error.headers?.get("retry-after")`) are always `undefined` for a Google error, so every Gemini retry falls through to the pure exponential backoff branch, `0.5 * 2^retryIndex` seconds capped at 8s with up to 25% negative jitter (`provider-retry.js:29-44`) — never the provider-requested delay Fiber's `docs/errors.md` and `docs/model-routing.md` describe for other protocols | Not directly comparable — rig has no retry loop at all in `rig-core` for any provider (`research/rig/README.md` §5); the question of honoring `Retry-After` is left to the embedding application everywhere, not specifically weaker for Gemini | pi only |
| Status codes pi retries for Gemini | `408, 409, 429`, or any `>= 500`, unless the SDK error carries an `x-should-retry` header (which Gemini's `ApiError` never does, per above, so that override is dead for this protocol) (`provider-retry.js:9-21`) | rig's shared `retryable_status`: `408, 425, 429`, or `500-599` (`error.rs:278-284`, verified directly) — note `409` (pi) vs `425` (rig) is the one status each includes that the other does not | disagree |
| Does the Gemini SDK itself ever retry before pi's wrapper sees the error? | No, by construction: the SDK's `apiCall` only retries when the caller supplies `retryOptions` (`index.mjs:13906-13920`); pi's `createClient`/`buildParams` never set `httpOptions.retryOptions`, so `patchedHttpOptions.retryOptions` is `undefined` and the SDK's own retry path (`DEFAULT_RETRY_ATTEMPTS=5`, `DEFAULT_RETRY_HTTP_STATUS_CODES=[408,429,500,502,503,504]`, `index.mjs:13493-13502`) is inert; `retryGoogleRequest`/`retryProviderRequest` is the sole retry mechanism actually exercised for Gemini | not applicable (rig has no client-side auto-retry to begin with) | pi only |
| Context-overflow message match for Gemini | `/input token count.*exceeds the maximum/i`, documented example `"The input token count (1196265) exceeds the maximum number of tokens allowed (1048575)"` (`utils/overflow.js:14,41`) | Not modeled as a distinct case in the Gemini wire; falls to the generic `ProviderError`/status classification the already-mined `research/provider-errors/README.md` describes for other protocols (Gemini itself was not reachable in that live probe: "`google-generative-ai` were not probed; no key reaches them") | pi only |
| Retry-worthy transport failure with no status | pi retries unconditionally when `error.status === undefined` (`provider-retry.js:15-16`) | rig's `retryable_status(None)` returns `false`; a missing status is instead judged by `transient_transport`, which retries only `StreamEnded` and backend `Instance` errors, not blindly (`error.rs:278-300`) | disagree |

## Disagreements

- Auth: pi (via the `@google/genai` SDK) always sends the API key as the `x-goog-api-key` header; rig always sends it as a `?key=` query parameter on the same `generateContent`/`streamGenerateContent` endpoints. Probe which one Gemini's real endpoint prefers or whether both work identically before Fiber picks one.
- `systemInstruction.role`: pi's plain-string system instruction is wrapped by the SDK as `{role: "user", parts: [...]}`; rig explicitly sets `{role: "model", parts: [...]}`. Confirm which role Gemini's backend actually expects or tolerates for `systemInstruction`.
- Tool parameter schema: pi defaults to full JSON Schema via `parametersJsonSchema`; rig always emits the OpenAPI-subset `parameters` field and pre-flattens `$ref`/`$defs`. Fiber needs to decide which field to target, since they accept different schema dialects.
- `toolConfig` mode: pi has a `VALIDATED` function-calling mode for Gemini 3+ strict sampling that rig's `FunctionCallingMode` enum does not model at all.
- Missing tool-call id handling: pi gates whether an `id` is sent at all on Gemini major version (omitted below v3) and normalizes ids to `^[a-zA-Z0-9_-]{1,64}$`; rig always sends whatever id the internal message carries, with no version gate or shape normalization.
- Synthetic tool-call ids: pi's generated id (`name_timestamp_counter`) is sent back to the model on replay as if it were the provider's own id; rig's synthetic id is kept purely as a local bookkeeping key and never presented upstream as a provider identity.
- Finish-reason mapping: pi collapses every non-STOP/MAX_TOKENS reason (including safety-filter reasons) into a single generic `"error"` stop reason; rig gives safety-filter reasons (`SAFETY`, `BLOCKLIST`, `PROHIBITED_CONTENT`, `SPII`) their own `ContentFilter` reason distinct from a raw `Other(reason)` catch-all.
- In-band `error` object mid-SSE-stream: pi's underlying SDK has a mid-stream error check that is effectively dead code for genuine `alt=sse` framing (a `JSON.parse` on raw SSE bytes throws before the check can fire), so a real Gemini in-band error is silently dropped as an empty chunk; rig explicitly recognizes `error` as one of its classified chunk keys and turns it into a proper `ProviderError`, feeding the shared retry table when the embedded `code` looks like an HTTP status.
- Retry-After: because the `@google/genai` SDK's `ApiError` never carries response headers, pi cannot honor a Gemini-issued `Retry-After`/`retry-after-ms` for this protocol and always falls back to plain exponential backoff; this is worth a live probe to confirm whether Gemini actually sends such a header on 429/5xx and whether Fiber's native protocol should read it directly rather than through an SDK-shaped error object.
- Retryable status codes differ by one entry each: pi retries HTTP 409 (not in rig's table); rig retries HTTP 425 (not in pi's table). Neither is Gemini-specific but both apply to this protocol's calls.
- Explicit prompt caching (`cachedContents` resource, TTL, cache-expired handling) exists only in rig; pi's Gemini adapter is implicit-cache-only (reads `cachedContentTokenCount`, never creates or references a cache resource). This is a capability gap either way Fiber decides to go, not a wire disagreement to resolve by probing.
- Multimodal function-response nesting (images inside `functionResponse.parts`) is gated by Gemini major version ≥ 3 in pi, sent unconditionally by rig regardless of model. Probe whether Gemini 1/2.x tolerates the nested-image shape or genuinely requires the separate-turn fallback pi uses.
