# Anthropic Messages wire protocol: pi vs rig

A fact table for the `anthropic-messages` wire protocol, read side by side from two
reference implementations. pi is `@earendil-works/pi-ai` 0.87.1, read from its compiled,
unminified `dist/` at
`/opt/homebrew/lib/node_modules/@earendil-works/pi-coding-agent/node_modules/@earendil-works/pi-ai/dist/`,
plus its pinned dependency `@anthropic-ai/sdk` 0.124.0 (`node_modules/@anthropic-ai/sdk/`),
which pi's `anthropic-messages.js` calls directly for transport, auth headers and retries.
rig is the checkout at `/Users/aakshintala/work/rig`, commit `42f4e06` (2026-09-26),
`crates/rig-core/src/providers/anthropic/`. Two documents already mined this pair and are
cited rather than repeated: `research/rig/README.md` (rig's own design, generic HTTP/SSE/
retry layer, prompt-cache byte-stability) and `research/provider-errors/README.md` (live
error-body and retry probe against muse and OpenRouter's Anthropic-shaped endpoints). Every
fact below was checked by reading the cited line; none are recalled from training data.

Marks: `agree` (both sources do the same thing), `disagree` (both implement it, differently),
`pi only`, `rig only`.

## 2. Stream event types and the terminal event

| Fact | pi | rig | Mark |
|---|---|---|---|
| Recognized top-level event types | `message_start`, `message_delta`, `message_stop`, `content_block_start`, `content_block_delta`, `content_block_stop` (`api/anthropic-messages.js:182-189`); anything else (including `ping`) is silently skipped by the SSE→event filter, and a literal SSE `event: error` is thrown as a JS `Error` before JSON parsing even runs (`api/anthropic-messages.js:308-310`) | `message`, `message_start`, `content_block_start`, `content_block_delta`, `content_block_stop`, `message_delta`, `message_stop`, `ping`, `error` (`providers/anthropic/streaming.rs:19-30`); `ping` is explicitly a known no-op, not an unrecognized tag (comment at line 63) | disagree (rig treats `ping` and unary `message` as first-class known events; pi silently drops anything not in its six-item set, so a `ping` frame is discarded before ever reaching the event switch) |
| Terminal event | `message_stop`; pi requires a stream that opened with `message_start` to also close with `message_stop`, else it throws `"Anthropic stream ended before message_stop"` (`api/anthropic-messages.js:301-331`) | `message_delta` carrying a `stop_reason` is rig's terminal frame, not `message_stop` (`providers/anthropic/streaming.rs:574-612`); a bare EOF with no such `message_delta` is truncation and no terminal record is synthesized (`streaming.rs:626-629`) | disagree (pi's stream-completeness check keys on `message_stop`; rig's keys on a `message_delta` with a stop reason and treats `message_stop` itself as content-lifecycle only) |
| Mid-stream `error` event | Anthropic-shape SSE `event: error` throws immediately with the raw data as the message (`api/anthropic-messages.js:308-310`) | `StreamingEvent::Error{error, raw}` requires the JSON body to carry an `error` field to classify as this variant at all (`streaming.rs:66-74`); sets `failed=true` and reports `ProviderError::from_provider_body(raw)` verbatim, preserving key order and any sibling fields (`streaming.rs:613-617`, `error.rs:413`) | agree (both fail the stream on this event; rig preserves the raw body byte-for-byte, pi surfaces only `sse.data`) |
| `message_start` with no message body | Not handled as a case; `event.message.id` etc. are read unconditionally (`api/anthropic-messages.js:403`) | Explicit Bedrock-compatibility no-op: an absent/null `message` on `message_start` is accepted silently (`streaming.rs:36-39,564-567`, comment "Bedrock-compat quirk") | rig only |
| Unrecognized nested delta tag | `parseJsonWithRepair`/switch on `event.delta.type` only handles `text_delta`, `thinking_delta`, `input_json_delta`, `signature_delta`; anything else falls through with no branch taken and no warning (`api/anthropic-messages.js:478-527`) | Preserved as `ContentDelta::Unknown(value)`, logged with a `tracing::warn!` naming only the delta's `type` tag (never its payload, since it may carry model output) and then skipped (`streaming.rs:94-96,318-324`) | disagree (rig logs a warning distinguishing "known event, unknown delta shape"; pi is silent) |
| Missing `type` field on a content delta | Would fail to match any `event.delta.type` branch and is silently dropped, same as an unrecognized tag | A hard deserialization error: "content delta is missing a `type` field" (`streaming.rs:152-155`) — distinguished from a merely unrecognized-but-present tag, which becomes `Unknown` | disagree |
| Non-JSON / malformed SSE data | `parseJsonWithRepair` first tries strict `JSON.parse`, then rewrites control characters and invalid escapes and retries once (`utils/json-parse.js:28-82`); a still-unparseable event throws with the raw event's `raw` lines attached (`api/anthropic-messages.js:314-327`) | No repair step; classification depends on `serde_json` parsing succeeding, no salvage attempt is described in this file | pi only |
| SSE framing (own parser vs shared) | Own hand-rolled line/field state machine (`decodeSseLine`, `flushSseEvent`, `consumeLine`, `nextLineBreakIndex`, `api/anthropic-messages.js:190-300`), same WHATWG-shaped rules as rig's (blank line flushes, `:`-prefixed lines are comments, CRLF/LF both accepted) | Own hand-rolled `SseFramer` (`http_client/framing.rs:38`, cited in `research/rig/README.md` §2); not reused here beyond citation | agree (both hand-roll a framer rather than use a library; not independently re-verified here beyond the citation) |

## 3. Tool-call assembly

| Fact | pi | rig | Mark |
|---|---|---|---|
| Keying accumulator | Anthropic's own `content_block` array `index` field, matched against the position in pi's own `output.content` array via `blocks.findIndex(b => b.index === event.index)` (`api/anthropic-messages.js:480,493,506,520,529`) | The content-block `index` becomes the block's key directly: `MintKind::Block.for_wire_index(index as u64)` for text/thinking, and the tool's own `id` (or a synthetic mint when empty) for tool calls (`streaming.rs:341-345,365-368`) | agree (both use Anthropic's `content_block_start.index`/`.id` as the natural key; neither needs an eviction/reuse guard because Anthropic, unlike some OpenAI-compatible gateways, never reuses an index before closing it — see `research/rig/README.md` §3 for the OpenAI-side eviction quirk that has no Anthropic analogue) |
| Partial JSON accumulation | String-concatenates every `input_json_delta.partial_json` fragment onto `block.partialJson`, then re-parses the whole buffer through `parseStreamingJson` on every delta (tolerant partial-JSON parse, falls back to `{}`) (`api/anthropic-messages.js:505-518`, parser at `utils/json-parse.js:90-112`) | Emits each raw delta immediately via `out.tool_arguments(key, partial_json)` for UI purposes and leaves final JSON assembly to a shared accumulator outside this file (`streaming.rs:284-289`); on `content_block_stop`, an empty accumulated string finalizes to `{}` and a malformed one surfaces as an error item rather than silently becoming `{}` (comment at `streaming.rs:446-448`, `UnparseableToolInput::Error` at line 450) | agree in effect (both treat "no bytes ever arrived" as `{}`), disagree in malformed-input handling: pi always produces a best-effort partial object (via `partial-json`) and never surfaces a parse failure to the caller; rig surfaces malformed input as an explicit error item |
| Parallel tool calls | Each new `content_block_start` with `type: tool_use` pushes a new block and only tracks `output.content.length - 1` as its index (`api/anthropic-messages.js:463-476`); no separate "current" pointer bug exists because indices are Anthropic's own array positions, not remapped | Only one `current_tool_call: Option<BlockId>` slot is held in `MessagesDecoder` at a time (`streaming.rs:237,368`), overwritten on the next `content_block_start` with `tool_use` — safe under Anthropic's strict start/stop-before-next-start-at-same-index framing, but structurally different from a map-of-open-calls design | disagree in mechanism (pi keeps a growing content array; rig keeps a single current-call slot), agree in outcome (both correctly assemble N sequential tool_use blocks with distinct ids) |
| Tool-name casing for Claude Code stealth mode | `toClaudeCodeName`/`fromClaudeCodeName` remap tool names to Claude Code's canonical casing (`Read`, `Bash`, etc.) on the way out for OAuth requests, and back on the way in (`api/anthropic-messages.js:41-76,467-469,1071`) | No equivalent renaming; tool names pass through unchanged | pi only |
| Empty/invalid tool input coercion | `parseStreamingJson` always returns an object, defaulting to `{}` (`utils/json-parse.js:90-93`) | `coerce_tool_input` on the request-encode side: object arguments pass through, a string decodes if it parses to an object, anything else becomes `{}` — this is request-side (replaying a tool call), not response-side accumulation (`completion.rs:774-783`) | agree (same normalization goal, applied on opposite sides of the wire: pi normalizes the decoded response, rig normalizes what it re-encodes) |

## 4. Reasoning/thinking blocks

| Fact | pi | rig | Mark |
|---|---|---|---|

| Redacted thinking, response decode | `redacted_thinking` content block becomes `{type:"thinking", thinking:"[Reasoning redacted]", thinkingSignature: event.content_block.data, redacted:true}` (`api/anthropic-messages.js:452-462`) | `Content::RedactedThinking{data}` maps to `ReasoningContent::Redacted{data}` via `out.reasoning_block(...)` (`streaming.rs:391-396`, mapping in `completion.rs:823-826`) | agree |

## 5. Prompt-cache markers

| Fact | pi | rig | Mark |
|---|---|---|---|
| `cache_control` placement | Up to 4 in practice, by construction rather than counting: the OAuth identity system block and/or the initial system-text block (`api/anthropic-messages.js:819-843`), the last non-deferred tool definition (`convertTools`, line 1177), and the last content block of the last user/system message (`api/anthropic-messages.js:1107-1132`) | Same three placement points, but counted and validated: static prefix (last non-deferred tool + system text) and conversation tail, capped by an explicit `MAX_CACHE_CONTROL_MARKERS = 4` (`completion.rs:1586`), enforced in `apply_prompt_cache_control` (`completion.rs:1809-1875`) | agree on placement, disagree on enforcement: pi relies on its own code never emitting more than 4 in the paths it controls (no runtime check), rig counts markers and returns `EncodeError::request(...)` if a caller's own `additional_params` tools push the count over budget (`completion.rs:1826-1831`) |
| Deferred tools skip the cache breakpoint | The `__pi_deferred_placeholder__` tool anchors deferred-tool scaffolding into the cached prefix from the first request so a later real deferred tool doesn't cause a full cache miss (`api/anthropic-messages.js:119-131`); the cache marker itself still goes on the last non-deferred tool | `final_cacheable_tool_idx` explicitly skips any tool with `defer_loading: true` when choosing where the last cache marker goes (`completion.rs:1588-1597`) | agree (same rule — the marker never lands on a deferred tool — independently arrived at) |
| Native mid-conversation tool add/remove | Fully modeled: `tool_addition`/`tool_removal` system-message blocks referencing tools by name, gated on `compat.supportsMidConvoSystemMessages && compat.supportsMidConvoToolChanges`, behind the `mid-conversation-tool-changes-2026-07-01` beta (`api/anthropic-messages.js:797-804,852-864,960-973`) | No `tool_addition`/`tool_removal` construction anywhere (`grep` for both terms in `providers/anthropic/` matches only pi-shaped test fixtures … actually zero matches in rig; rig only *reads* `defer_loading` defensively for cache placement, it never emits deferral scaffolding itself) | pi only |
| TTL values | `"short"` (default, resolves to Anthropic's default 5-minute ephemeral cache, no `ttl` field sent) or `"long"` (sends `ttl: "1h"`, only when `model.compat.supportsLongCacheRetention`, default true) (`api/anthropic-messages.js:21-40`); per-model catalog confirms these as literal seconds, `promptCache: {short: 300, long: 3600}` (e.g. `providers/data/anthropic.json`, `claude-fable-5` entry) | `CacheTtl::FiveMinutes` (default, serializes to no `ttl` field via `#[serde(rename="5m")]` sibling omission — actually always serializes `"5m"` explicitly unless `None`, see enum at `completion.rs:182-191`) or `CacheTtl::OneHour` (`"1h"`) | agree on the two TTL values and their meaning; rig always allows the caller to name a TTL explicitly per breakpoint (`with_static_prefix_cache_ttl`, `wire.rs:403-428`), pi only exposes one retention choice per request that applies uniformly |
| 1-hour markers must precede 5-minute markers | Not validated or documented anywhere in pi's code | Explicit validation: `validate_cache_control_ttl_order` walks tools, system, messages and the top-level marker in wire order and errors if a `1h` marker appears after a `5m` one has been seen (`completion.rs:1659-1715`) | rig only |
| Automatic/top-level caching mode | Not implemented; pi only ever sets `cache_control` on individual content blocks, never a top-level `cache_control` field | `Messages::with_automatic_caching()`/`with_automatic_caching_1h()` set a top-level `cache_control` field the API itself advances as the conversation grows, no beta header required (`wire.rs:359-401`, field on `AnthropicCompletionRequest` at `completion.rs:1568-1572`) | rig only |
| Retention "none" | `cacheRetention: "none"` disables cache markers and also disables session-affinity headers, since there's no session identity worth pinning without caching (`api/anthropic-messages.js:32-34,377-378`) | No retention-off mode; caching is simply not requested (`prompt_caching: false` default, `wire.rs:270-275`) | disagree (pi has a named "none" mode with a side effect on session headers; rig's "off" state is just never opting in, no session-header interaction exists to disable) |
| Cache read/write usage reporting | `usage.cacheRead`/`usage.cacheWrite` from `cache_read_input_tokens`/`cache_creation_input_tokens`; separately, `usage.cacheWrite1h` from `usage.cache_creation.ephemeral_1h_input_tokens` (`api/anthropic-messages.js:418-420`) | `Usage.cache_creation: Option<CacheCreation>` with `ephemeral_5m_input_tokens`/`ephemeral_1h_input_tokens` fields (`completion.rs:98-108`), and the terminal `message_delta`'s `PartialUsage` carries the same breakdown forward from `message_start` since the terminal frame itself omits it (`streaming.rs:172-176`, comment lines) | agree (both report a per-TTL cache-write breakdown; same two TTL buckets) |

## 6. Error bodies, retry signals, context-overflow shapes

## Disagreements

- Endpoint path: pi's SDK posts to `/v1/messages?beta=true`; rig posts to `/v1/messages`. Probe whether the query param changes any server-side behavior Fiber would need to replicate, or is purely an SDK routing artifact.
- Terminal stream event: pi requires `message_stop` to consider a stream complete; rig's terminal frame is `message_delta` carrying a `stop_reason`. Confirm which one Anthropic actually guarantees last, live.
- Retryable status codes differ at the edges: pi retries `409`, not `425`; rig retries `425`, not `409`. Neither has been seen live from Anthropic itself in this repo's probes — worth a live check of whether Anthropic ever returns either code.
- A response with no HTTP status at all: pi treats this as retryable by default; rig treats it as not retryable. This is a meaningful default to pick deliberately for Fiber rather than inherit from either.
- `tool_choice` without `tools`: pi sends it anyway (would 400 on real Anthropic); rig strips it. Confirm Anthropic's real behavior and make sure Fiber matches rig's guard.
- Redacted thinking across a model switch: pi drops it; rig (as read here) always resends it verbatim regardless of model. Decide Fiber's own rule explicitly rather than default to either.
- Cache-marker budget enforcement: pi never counts (relies on its own code shape staying under 4); rig counts and errors past 4. Fiber should count, per rig's example — silent truncation of a cache marker is worse than a clear encode-time error.
- Unknown/forward-compatible `stop_reason`: pi throws a hard error; rig accepts anything via `Other(string)`. Decide which failure mode Fiber wants when Anthropic ships a new stop reason.
- Strict-tool-schema failure mode: pi can reject a tool definition outright (unless a lenient policy is set); rig always downgrades unsupported keywords into descriptive text and never fails. Decide Fiber's default.
- `x-should-retry`/`retry-after-ms`/`retry-after` headers: pi reads and acts on all three; rig documents `retry-after` only as an example for callers and never reads any of the three itself. Fiber needs its own explicit retry-header contract — probe whether Anthropic or its gateways (muse, OpenRouter — see `research/provider-errors/README.md`) actually send `x-should-retry` or `retry-after-ms` in practice, since neither has been independently confirmed live in this repo's probes.
