Fact table for the OpenAI Chat Completions wire protocol (`POST /chat/completions`,
SSE when streamed), as spoken by OpenAI itself and by the many
completions-compatible vendors pi and rig both support. Pi is
`@earendil-works/pi-ai` 0.87.1
(`/opt/homebrew/lib/node_modules/@earendil-works/pi-coding-agent/node_modules/@earendil-works/pi-ai/dist`),
compiled but unminified, read at `api/openai-completions.js`,
`api/openai-prompt-cache.js`, `api/transform-messages.js`,
`api/simple-options.js`, `api/constrained-sampling.js`,
`api/github-copilot-headers.js`, `utils/provider-retry.js`, `utils/overflow.js`,
`utils/json-parse.js`, `utils/error-body.js` and `compat.js`. Rig is
`~/work/rig` at commit `42f4e06` (2026-09-26), read at
`crates/rig-core/src/providers/openai/wire.rs`,
`crates/rig-core/src/providers/openai/wire/{chat,dto,dialects,route}.rs`,
`crates/rig-core/src/providers/openai/completion/mod.rs`,
`crates/rig-core/src/providers/internal/{openai_chat_completions_compatible,tool_call_bridge,chunk_lifecycle,wire,tool_call_ids}.rs`,
`crates/rig-core/src/completion/message.rs` and `crates/rig-core/src/error.rs`.
`research/rig/README.md` (already mined) covers rig's shared SSE framer,
prompt-cache byte-stability stance, and error taxonomy at a level above any
one protocol, and `research/provider-errors/README.md` covers live-probed
error bodies for `openai-completions` through muse and OpenRouter — both are
cited rather than repeated. This table covers the Chat Completions wire only;
rig's `openai-responses` route (selected by default for OpenAI, xAI and
ChatGPT) is a separate wire not covered here.

## 2. Stream event types and the terminal event

| Fact | pi | rig | Mark |
|---|---|---|---|
| Frame recognition (no `type` discriminator on this wire) | delegated entirely to the third-party `openai` npm SDK's own SSE parsing (`import OpenAI from "openai"`, `openai-completions.js:1`); pi's own code never inspects a raw frame | `internal/wire.rs:95-115` `classify_chat_completions_frame` — a frame is a chunk if it says `"object":"chat.completion.chunk"` or carries `choices`; a duplicate `object`/`choices` key is `Corrupt` outright | rig only (pi has no source of its own to cite for this step) |
| `[DONE]` sentinel | consumed by the `openai` SDK's stream iterator (`openai-completions.js:353`, `for await (const chunk of openaiStream)`); no pi code names the literal string | `wire/chat.rs:1261-1265` — `data == "[DONE]"` is `ChatEvent::Done`, a deferred-terminal marker distinct from any usage/`finish_reason` chunk | rig only |
| In-band 200-status error envelope | no decoder-level classification; the SDK throws, and pi's catch block appends `error.error.metadata.raw` (OpenRouter) to the surfaced message if not already present (`openai-completions.js:503-510`) | `internal/openai_chat_completions_compatible.rs:13-38` — a frame carrying a nonempty `"error"` and empty/absent `choices` is `ChatEvent::Failure`, flushing any tool calls already decoded first (`wire/chat.rs:1269-1271,1312-1318,1362-1368`) | disagree — pi has no frame-level model for this and only string-appends extra detail after the SDK's own throw; rig classifies it as a first-class terminal event with its own flush ordering |
| `finish_reason` vocabulary | `openai-completions.js:1190-1212` — `stop`/`end`→stop, `length`→length, `function_call`/`tool_calls`→toolUse, `content_filter`→error (with message), `network_error`→error (with message), anything else→error | `internal/openai_chat_completions_compatible.rs:45-54` — `stop`→Stop, `length`\|`max_tokens`\|`model_length`→Length, `tool_calls`\|`function_call`→ToolCalls, `content_filter`→ContentFilter (its own successful variant, never an error), anything else preserved verbatim as `Other(string)`; no `network_error` case exists | disagree — pi turns a `content_filter` or `network_error` finish reason into a stream error; rig keeps `content_filter` as a normal terminal reason and has no `network_error` mapping at all |
| Upstream/native finish reason (gateway relay) | not read; whatever `finish_reason` string arrives is authoritative (`openai-completions.js:373-380`) | `wire/dto.rs:221-224`; `wire/chat.rs:867-885`; `internal/openai_chat_completions_compatible.rs:58-68` — consults a `native_finish_reason` string (with a broader synonym table: `end_turn`, `stop_sequence`, `tool_use`, `safety`, `blocklist`, `prohibited_content`, `spii`) only when the normalized field is absent/empty, gated to OpenRouter (`dialects.rs:328`) | rig only |
| Usage-chunk placement fallback | `openai-completions.js:362,368-372` — falls back to `choice.usage` when `chunk.usage` is absent, documented as a Moonshot quirk | `wire/dto.rs:247` `ChatFrame.usage` — only the top-level frame field is read; no choice-level usage fallback exists | pi only |
| Cached-token usage field | `openai-completions.js:1162-1163` — checks `prompt_tokens_details.cached_tokens`, then `prompt_cache_hit_tokens` (DeepSeek), then a bare `cached_tokens` (Kimi) | `completion/mod.rs:1187-1242,1311-1336`; `wire/dto.rs:192-198` — reads `prompt_tokens_details.cached_tokens` or Mistral's top-level `num_cached_tokens`, falling back to DeepSeek's `prompt_cache_hit_tokens` only when the OpenAI field is absent | agree on the two providers both name explicitly (DeepSeek, generic `cached_tokens`); pi has one further fallback (bare `cached_tokens`) rig's DTO has no field for |
| Reasoning-token usage | `openai-completions.js:1176,1183` — `completion_tokens_details.reasoning_tokens`; notes `completion_tokens` already includes it | `wire/chat.rs:1391-1393`; `completion/mod.rs:1210-1215,1330-1333` — same field, into `AdapterUsage.reasoning_tokens` and normalized `Usage.reasoning_tokens` | agree |
| Streamed text-delta source | `openai-completions.js:382-393` — reads `choice.delta.content`, requiring non-null and non-empty | `wire/dto.rs:103-107,153-163` `delta_text()` — prefers non-empty `content`, falling back to non-empty `refusal` text when content is empty or absent | rig only (extra refusal-to-text fallback) |

## Disagreements

- Output-token cap field name: pi picks `max_tokens` vs `max_completion_tokens` per a hand-maintained vendor allow-list (sending Groq/Mistral/Perplexity/HuggingFace/Venice `max_completion_tokens`); rig defaults every non-OpenAI dialect to `max_tokens` and rewrites only for OpenAI's own reasoning-family model names.
- `stream_options.include_usage`: pi asks every vendor, including OpenRouter and Mistral; rig deliberately omits it for OpenRouter, Mistral, Perplexity and Mira.
- Anthropic-style `cache_control` coverage: pi marks the system prompt, last tool and last conversation message with an optional `ttl`; rig marks only the system prompt, opt-in, OpenRouter only, no `ttl`.
- Strict tool-schema granularity: pi decides strictness per tool; rig applies one `strict_tools` flag to the whole request.
- In-band 200-status error frame: pi has no decoder-level model, only a post-hoc string append after the SDK throws; rig classifies it as a first-class terminal event with defined flush ordering.
- `finish_reason` handling of `content_filter`/`network_error`: pi turns both into a stream error; rig keeps `content_filter` as an ordinary terminal reason and has no `network_error` case.
- `n > 1` candidate selection: pi always reads array position 0; rig selects the choice whose `index` field is 0 or absent.
- Tool-call accumulator keying: pi falls back from index to a by-id lookup; rig keys strictly by wire index.
- Partial tool-call JSON parse timing: pi re-parses a best-effort object on every delta; rig parses once, at block close.
- Tool-call id normalization for replay: pi post-processes a pipe-separated Responses-API-shaped id and truncates to 40 chars for the official provider; rig allocates its own request-scoped id table and never sees that shape.
- Malformed/truncated tool arguments: pi always produces some object (never hard-errors); rig hard-errors on unparseable arguments unless the finish reason was `Length`.
- Streamed reasoning field names: pi recognizes `reasoning_content`, `reasoning` and `reasoning_text`; rig's DTO has no slot for `reasoning_text`.
- Assistant-message reasoning echo field: pi picks the field name from the block's recorded origin; rig always emits `reasoning_content`, rewritten to `reasoning` only for OpenRouter.
- Reasoning-as-plain-text fallback: pi requires an explicit (never-set-by-default) compat flag; rig does this by default whenever structured replay is off.
- Streamed `reasoning_details` entries: pi merges all three types (summary/encrypted/text) while streaming; rig's streaming path only handles `Encrypted` and a `Text` detail's signature, silently dropping summary content and text-detail plaintext until a non-streamed reply.
- Cache-read/write usage accounting: pi subtracts both cache-read and cache-write tokens from normalized `input`; rig subtracts neither.
- Retryable status codes: pi retries `409` but not `425` and honors an `x-should-retry` header override; rig retries `425` but not `409` and has no header-override concept.
- In-band 200-status error envelope (retry angle): pi reacts to whatever the underlying SDK throws; rig classifies the frame itself before any exception exists.
- Provider error-body normalization: pi normalizes across several third-party SDKs' differing error shapes; rig has one transport and passes the raw response through unmodified.
- Transient-transport retry: rig retries a bare stream-ended transport failure; pi's retry guard only recognizes SDK-shaped `{status, headers}` errors and retries nothing else.
- Declared compat-field scope: pi's ~26 fields cover chat completions alone; rig's 39 top-level fields (86 once nested structs are counted, per `research/rig/README.md` §6) also cover embeddings, transcription, images, speech and Responses.
- How the flag set is chosen: pi auto-detects from provider id/URL at request time with a per-field override; rig selects a whole compiled `Dialect` constant at configuration time and never infers from a URL or provider string (ADR 0007's distinction).
- DeepSeek quirks: pi forces an empty `reasoning_content`; rig echoes `index` on tool calls and flattens content to a string — neither replicates the other's rule.
- Groq quirks: rig folds native tools and strips reasoning on replay; pi has neither, and the two disagree on the output-cap field for Groq specifically.
- Moonshot quirks: pi has no `tool_choice` coercion; rig has no reasoning-effort/cache-retention distinction (having none at all on this wire).
- OpenRouter quirks: pi gates developer-role/cache-control per underlying model id prefix; rig gates `native_finish_reason`/`reasoning_details`/`upstream_reasoning_issuer` on the whole dialect.
- Reasoning-family output-cap granularity: pi decides per vendor (a static allow-list); rig decides per model-name pattern, scoped only to OpenAI's own dialect.
