## Disagreements

- Retry status-code tables differ: pi retries HTTP 409, not 425; rig retries 425, not 409. Needs a probe against a real gateway that returns one or the other.
- pi always sends `store: false`; rig leaves OpenAI's default (`store: true`) unless the caller or the codex dialect sets it. Decide Fiber's own default deliberately rather than inheriting either.
- pi auto-requests `reasoning.encrypted_content` only for an explicit non-off reasoning config (or always for xAI); rig auto-requests it for any `reasoning` object at all, including an "off" effort. Probe whether requesting it for an off-effort reasoning call is harmless or rejected.
- pi's normalized "input tokens" usage figure subtracts `cached_tokens` and `cache_write_tokens`; rig's is the raw wire `input_tokens`, cache-inclusive. Fiber must pick one convention and document it, since the two are not comparable numbers.
- pi never populates the top-level `instructions` field for OpenAI's own Responses dialect (everything stays inline in `input`); rig's OpenAI dialect defaults to lifting the leading system-message run into `instructions`. Probe whether OpenAI's own backend treats the two placements identically for cache and behavior.
- pi omits a tool's `strict` key entirely when it believes the provider doesn't support strict mode, which (per OpenAI's own semantics, as rig's code comment states) leaves that provider defaulting to attempt-strict-mode; rig always sends an explicit `strict: true/false`. Worth checking which is actually safer against a real non-strict-mode provider.
- On `response.failed`, pi discards any partially-streamed content before raising; rig flushes fully-completed tool calls first, then raises. Decide which behavior Fiber wants for a failed turn that had already produced tool calls.
- pi throws immediately when a stream ends without a terminal event; rig silently withholds the terminal record and leaves "was this a truncation?" to its caller. Fiber needs an explicit decision here, not an inherited default.
- pi maps `in_progress`/`queued` response status to `stopReason: "stop"` (flagged in its own source as "wonky") and throws on any genuinely unrecognized status; rig maps both to "no finish reason yet" and never throws on an unknown status. Fiber should not inherit pi's admittedly-wrong mapping.
- pi's partial-JSON tool-argument parser (`partial-json` + a custom repair pass) best-effort-parses every incomplete delta for live display; rig never attempts to parse an incomplete buffer and only degrades to raw-text passthrough at the authoritative event. If Fiber wants live partial-argument display, it needs pi's approach; if it only needs correctness at completion, rig's simpler approach suffices.
- pi's `store: false` replay resends the exact captured wire JSON for a reasoning item verbatim; rig reconstructs the request-shaped reasoning object field-by-field from its own typed decode, which risks silently dropping an unmodeled sibling field on a reasoning item specifically (unlike rig's `Output::Compaction`/`Output::Unknown` catch-alls, which do preserve unmodeled *item types* verbatim). Worth a live probe: does OpenAI ever send an undocumented field on a `reasoning` output item that a strict field-by-field rebuild would lose?
